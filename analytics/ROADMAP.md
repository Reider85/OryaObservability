## 1. Назначение и принципы roadmap

### 1.1. Контекст

Настоящий документ разворачивает §12 «Roadmap внедрения» из `ARCHITECT.md` в полный план реализации observability-стека для LLM-агентов. Если `ARCHITECT.md` фиксирует **что** строится (пятислойная архитектура: Logs/Traces, Metrics, Eval/Quality, Security, Cost/Budget) и **почему** именно так (ТРИЗ-анализ противоречий и 15 улучшений), то `ROADMAP.md` отвечает на вопрос **как и в каком порядке** это внедрять — от пилота до идеальной ТРИЗ-архитектуры.

Документ ориентирован на технических лидов и backend-разработчиков: каждый эпик декомпозирован до уровня тикета (3–5 задач на эпик), имеет явное ТРИЗ-обоснование, DoD и KPI. Это позволяет напрямую перенести эпики в Jira/Linear/YouTrack без дополнительной декомпозиции.

### 1.2. Принципы уровневой декомпозиции

Roadmap разбит на четыре уровня, каждый из которых является самостоятельной поставкой ценности (shippable increment) и не нарушает работу предыдущего:

1. **MVP** — минимально жизнеспособная observability: один пилотный агент, Logs/Traces + Cost, без eval и security. Цель — доказать, что observability не блокирует продакшен.
2. **CRITICAL** — критический минимум для production: guardrail, eval, drift detection, tiered storage. Без этого уровня нельзя пускать агента на реальных пользователей.
3. **production-ready** — полноценный production-grade observability со всеми SLO, адаптивным сэмплированием, tree-compression для длинных трейсов.
4. **Улучшения production-ready** — целевая ТРИЗ-архитектура из §11 `ARCHITECT.md`: sidecar-SDK, federation, cost-aware routing, движение к ИКР.

**Ключевое правило — non-contradiction.** Ни одна задача уровня N не отменяет решений уровня N-1. ТРИЗ-улучшения из §11 `ARCHITECT.md` применяются инкрементально: например, sidecar-SDK (Улучшение #11) вводится только на уровне 4, но не ломает thin client API, заложенный в уровне 1 — он остаётся тем же контрактом, просто реализация переносится в sidecar.

## 4. Уровень 1 — MVP (4–6 недель)

### 4.1. Цель уровня

Базовое покрытие слоёв **Logs/Traces** и **Cost** для одного пилотного агента на Python. Доказать, что observability-инструментация не блокирует продакшен-логику и даёт немедленную диагностическую ценность: trace с привязкой стоимости виден в UI. Слой Metrics — минимальный (только технические метрики для overhead-контроля). Слои Eval, Security, Federation — out-of-scope.

Этот уровень воспроизводит §12.1 `ARCHITECT.md` с расширением до эпиков и задач. Архитектурных отклонений от §3–§7 нет — берётся минимально жизнеспособное подмножество.

### 4.2. Эпики уровня

#### Эпик E1.1 — Python SDK каркас (декораторы + context manager)

**Описание.** Реализовать ядро SDK из §6.2 `ARCHITECT.md`: классы `SpanContext`, `Span`, `ObservabilitySDK` с декоратором `@agent_observed(agent_id, version)` и контекстным менеджером `async with sdk.llm_call(ctx, model, provider)`. Внутреннее представление span'а — Python dataclass, сериализуемый в OTLP-совместимый protobuf (подготовка к уровню 4 — Protobuf-first).

**ТРИЗ-обоснование.** Принцип 28 (замена механической схемы): sync-логирование заменяется на async-first API с context manager. Принцип 25 (самообслуживание): SDK сам управляет контекстом span'а через `_obs_ctx`, разработчик агента не передаёт его явно в каждый вызов.

**Задачи:**
- T1.1.1. Спроектировать и зафиксировать `SpanContext` dataclass с полями `trace_id`, `span_id`, `parent_span_id`, `agent_id`, `agent_version`, `user_id`, `session_id` (как в §6.2).
- T1.1.2. Реализовать `Span` dataclass с атрибутами `attributes: dict`, `events: list`, таймстампами.
- T1.1.3. Реализовать декоратор `agent_observed(agent_id, version)` — оборачивает async-функцию `run()`, создаёт root span типа `agent.loop`.
- T1.1.4. Реализовать контекстные менеджеры `llm_call()`, `tool_call()` с типами span'ов `llm.call`, `tool.call` (перечень типов из §2.3).
- T1.1.5. Добавить флаг `enabled` в конфиг SDK — при `False` декораторы становятся no-op (zero-overhead при отключении, требование §6.1).

**DoD.** SDK импортируется как `from agent_obs import ObservabilitySDK`, декоратор применяется к async-классу агента без изменения бизнес-логики. При `enabled=False` overhead < 1 микросекунды на вызов.

**KPI.** API-покрытие: 3 из 9 типов span'ов из §2.3 (`agent.loop`, `llm.call`, `tool.call`). Остальные 6 типов переносятся на уровень 2.

#### Эпик E1.2 — OTLP-экспорт в Langfuse (self-hosted)

**Описание.** Реализовать `LangfuseExporter` по контракту `BaseExporter` (§6.4 `ARCHITECT.md`). SDK отправляет батчи span'ов в Langfuse через его public API. Langfuse разворачивается self-hosted в одном Docker-контейнере с Postgres для метаданных.

**ТРИЗ-обоснование.** Принцип 5 (объединение): единый OTLP-протокол как transport-контракт. Принцип 12 (эквипотенциальность): внутреннее представление span'а уже OTLP-совместимое, поэтому замена экспортёра на Phoenix или stdout не требует изменения SDK-логики.

**Задачи:**
- T1.2.1. Развернуть Langfuse self-hosted (docker-compose: langfuse + postgres + redis).
- T1.2.2. Реализовать `LangfuseExporter.export(batch: list[Span])` — батчинг до 512 span'ов, ретрай с экспоненциальной задержкой.
- T1.2.3. Реализовать `LangfuseExporter.flush()` — досылка остатков при shutdown.
- T1.2.4. Добавить аутентификацию по public/secret key, настроить TLS для продакшена.

**DoD.** В UI Langfuse виден трейс пилотного агента с деревом span'ов, атрибутами и событиями. Батч из 512 span'ов долетает за < 200 мс p95.

**KPI.** Доставка: 100% трейсов пилотного агента видны в UI в течение 5 секунд p95 после завершения `agent.loop`.

#### Эпик E1.3 — Tail-sampler с фиксированной политикой

**Описание.** Внедрить tail-sampling processor в OTel Collector между SDK и Langfuse. Политика — фиксированная, без адаптации (адаптивность переносится на уровень 3): 100% трейсов с ошибками, 100% трейсов с превышением budget, 100% трейсов с security-инцидентом (заглушка — на MVP security нет, но поле есть), 10% обычных трейсов.

**ТРИЗ-обоснование.** Принцип 16 (частичное или избыточное действие): «чуть меньше» — 10% обычных трейсов вместо 100% дают 10× экономию storage без потери возможности дебага (худшие трейсы всегда есть). Стандарт 2.2.4 (динамизированный веполь) закладывается как цель, но не реализуется — это уровень 3.

**Задачи:**
- T1.3.1. Развернуть OTel Collector с custom processor'ом `llm_tail_sampler`.
- T1.3.2. Реализовать policy: `error_status = true` → keep 100%; `cost.usd > threshold` → keep 100%; random 10% — keep.
- T1.3.3. Добавить метрику `tail_sampler_kept_ratio` для контроля доли сохранённых трейсов.
- T1.3.4. Настроить content-sampling: полный текст промпта — только у 10% сохранённых трейсов, у остальных — SHA-256-хэш + длина.

**DoD.** При нагрузке 100 RPS на пилотного агента в Langfuse попадает 10–15% трейсов (с учётом 100% для ошибок). Storage растёт < 5 ГБ/день.

**KPI.** Доля сохранённых трейсов: 10–15% от общего числа. Доля потерянных «интересных» трейсов: 0% (по политике).

#### Эпик E1.4 — Cost-трекинг как атрибут span'а

**Описание.** Реализовать функцию `_compute_cost(usage, model)`, вычисляющую стоимость вызова LLM по формуле из §3.5 `ARCHITECT.md`: `cost = tokens.input * price.input_per_1k / 1000 + tokens.output * price.output_per_1k / 1000`. Цена берётся из `price_book` (YAML-файл с `valid_from`/`valid_to`). Записывать cost как атрибут `cost.usd` span'а `llm.call` (не как отдельную сущность — антипаттерн §8.4).

**ТРИЗ-обоснование.** Принцип 26 (копирование): вместо отдельной биллинг-системы (копия cost-данных в другом месте) cost-атрибут живёт в трейсе. Принцип 12 (эквипотенциальности): `price_book` версионирован, в span'е фиксируется `cost.price_book_version` — это позволяет реконсиляцию с биллингом провайдера без противоречий.

**Задачи:**
- T1.4.1. Создать `price_book.yaml` для топ-5 моделей (gpt-4o, gpt-4o-mini, claude-3.5-sonnet, claude-3-haiku, gemini-1.5-pro).
- T1.4.2. Реализовать загрузку `price_book` с валидацией `valid_from`/`valid_to`.
- T1.4.3. Реализовать `_compute_cost()` с поддержкой cached tokens (отдельная цена).
- T1.4.4. Атрибуты span'а `llm.call`: `tokens.input`, `tokens.output`, `tokens.cached`, `cost.usd`, `cost.price_book_version`.
- T1.4.5. Экспортировать метрику `cost_per_request_usd` (gauge) с лейблами `agent_id`, `model`.

**DoD.** В UI Langfuse на span'е `llm.call` видны все cost-атрибуты. Сумма cost-атрибутов по трейсу совпадает с биллингом OpenAI ±5% (реконсиляция).

**KPI.** Точность cost-учёта: ±5% от реальной стоимости биллинга провайдера.

#### Эпик E1.5 — Базовый trace-viewer через Langfuse UI

**Описание.** Использовать встроенный trace-viewer Langfuse без кастомизации. Настроить лейблы в UI: `agent_id`, `model`, `cost.usd`, `status`. Создать один saved query «трейсы с ошибками за последние 24 часа» для дебага.

**ТРИЗ-обоснование.** Принцип 5 (объединение): не делаем свой UI, переиспользуем Langfuse. Кастомный trace-tree viewer (с on-demand drill-down) переносится на уровень 3 — пока не оправдан.

**Задачи:**
- T1.5.1. Настроить маппинг span-атрибутов в лейблы Langfuse UI.
- T1.5.2. Создать 3 saved query: «ошибки 24ч», «cost > $0.05», «loop > 10 шагов».
- T1.5.3. Написать README для команды поддержки: как искать трейс по `trace_id`.

**DoD.** Разработчик может за < 30 секунд найти трейс по `trace_id` или по фильтру «ошибки 24ч».

**KPI.** Time-to-trace: < 30 секунд на поиск конкретного трейса.

#### Эпик E1.6 — In-process ring buffer + async export (fire-and-forget)

**Описание.** Реализовать `asyncio.Queue(maxsize=100_000)` как ring buffer между instrumentation и exporter (как в §6.2 `ARCHITECT.md`). Worker-таска читает из буфера, формирует батчи до 512 span'ов с drain-окном 50 мс, fan-out на все экспортёры. При переполнении буфера — drop с инкрементом метрики `dropped_spans` (антипаттерн §8.5: observability никогда не должна блокировать бизнес-логику).

**ТРИЗ-обоснование.** Принцип 28 (замена механической схемы): sync-логирование → lock-free ring buffer + async export. Overhead падает до наносекунд на операцию. Принцип 22 (превращение вреда в пользу): переполнение буфера — это «вред», но метрика `dropped_spans` превращает его в сигнал для SRE: «нужно масштабировать collector или снизить сэмплинг».

**Задачи:**
- T1.6.1. Реализовать `_ring_buffer: asyncio.Queue` с `maxsize=100_000`.
- T1.6.2. Реализовать `_export_worker()` с drain-окном 50 мс и batch size ≤ 512.
- T1.6.3. При `QueueFull`: drop, инкремент `dropped_spans_total` (Prometheus counter), лог warning.
- T1.6.4. При shutdown: `flush()` ожидает досылки всех span'ов из буфера (timeout 5 секунд).
- T1.6.5. Тест: при 10 000 RPS агент не должен блокироваться > 1 мс на instrumentation.

**DoD.** При отключении Langfuse (network failure) агент продолжает работать без ошибок. Через 60 секунд буфер переполняется, `dropped_spans` растёт, бизнес-логика не ломается.

**KPI.** Overhead на instrumentation: < 5% CPU при 100 RPS. Доля потерянных span'ов при нормальной нагрузке: 0%.

### 4.7. Rollback-стратегия

- **Технический rollback:** `sdk.enabled = False` в конфиге агента → декораторы становятся no-op, агент продолжает работу без observability. Трейсы перестают идти в Langfuse, но бизнес-логика не страдает.
- **Частичный rollback:** отключить один из экспортёров (например, Phoenix, если он добавлен) без отключения Langfuse.
- **Storage rollback:** снизить `tail_sampler_kept_ratio` с 10% до 1% через конфиг OTel Collector без передеплоя агента.
- **Полный демонтаж:** удалить SDK из агента (вернуть коммит), остановить Langfuse и Collector. Никаких миграций данных — на MVP ничего критичного не хранится.

### 5.2. Эпики уровня

#### Эпик E2.1 — Guardrail Engine (PII detection + injection detection)

**Описание.** Реализовать локальный `GuardrailEngine` (§4.2 `ARCHITECT.md`), работающий синхронно в процессе агента в критических точках: перед записью лога, перед tool-call'ом. Состоит из двух подвижков: PII-детектор (регулярки + CRF-модель для email/телефон/ИНН/паспорт) и injection-классификатор (small BERT, например `deepset/deberta-v3-base-prompt-injection`). Задержка — < 5 мс на проверку (требование §4.2).

**ТРИЗ-обоснование.** Стандарт 2.2.1 (переход к внутреннему комплексу веполя): guardrail добавляется как внутреннее «поле» безопасности внутри SDK, а не как внешний WAF. Это устраняет окно между проверкой и записью, где PII может утечь в логи контейнера.

**Задачи:**
- T2.1.1. Реализовать `PIIDetector` с регулярками для email/phone/INN/passport/payment.
- T2.1.2. Интегрировать CRF-модель (Presidio или аналог) для медицинского PII.
- T2.1.3. Интегрировать `deberta-v3-base-prompt-injection` для injection-детекции.
- T2.1.4. Реализовать `GuardrailEngine.check_input(text) -> GuardrailVerdict` с `score`, `verdict` (clean/flag/block).
- T2.1.5. Встроить guardrail в `_enqueue()` SDK: PII-маскинг синхронно, до любой передачи (антипаттерн §8.3).

**DoD.** Любой PII в промпте маскируется до записи в ring buffer. Injection с score > 0.85 блокирует вызов LLM и пишет audit-event.

**KPI.** Latency guardrail: < 5 мс p99 на проверку. PII recall: > 95% на тестовом датасете. Injection F1: > 0.90.

#### Эпик E2.2 — Field-aware PII masking (по типу поля)

**Описание.** PII-маскинг применяется по-разному к разным полям span'а: `system_prompt` — без маскинга (там нет пользовательского PII по архитектурному решению), `user_message` — полный маскинг, `tool_output` — частичный (маскируем только PII-поля из ответа БД, например колонку `email` в SQL-ответе). Это разрешает противоречие ТП-3 (§10.4): privacy сохранён, debuggability — 90%.

**ТРИЗ-обоснование.** Принцип 3 (местное качество): разные части объекта (span'а) выполняют разные функции — `system_prompt` это контракт, `user_message` это приватный ввод. Применение blanket-маскинга ко всем полям снижает debuggability без увеличения privacy.

**Задачи:**
- T2.2.1. Реализовать `FieldMasker` с конфигом по типам полей (YAML).
- T2.2.2. Для `tool_output`: парсить известные tool-схемы (SQL — колонки, REST — JSON-path), маскировать только PII-поля.
- T2.2.3. Сохранять `pii.redacted_fields: ["user_message.email", "tool_output.rows[0].phone"]` в атрибутах span'а.
- T2.2.4. Тест: debug-сессия может восстановить контекст без PII на 90% (по выборке из 100 трейсов).

**DoD.** На span'е `llm.call` атрибут `pii.redacted_fields` содержит список замаскированных полей. `system_prompt` виден в UI полностью.

**KPI.** Debuggability score (по выборке): ≥ 90% случаев можно дебажить без vault recovery.

#### Эпик E2.3 — Vault для PII-восстановления через MFA

**Описание.** Mapping «маска → оригинал» хранится в зашифрованном vault (HashiCorp Vault или AWS KMS + DynamoDB). TTL на запись — 24 часа. Доступ к оригиналу требует MFA-аутентификации (TOTP) и логируется в audit trail. Это разрешает ТП-3 по Стандарту 5.1.1: противоречивые свойства (masked и accessible) разделены в пространстве (логи — masked, vault — accessible).

**ТРИЗ-обоснование.** Принцип 26 (копирование): оригинал PII заменяется копией (маской), а оригинал хранится отдельно. Стандарт 5.1.1 (разрешение физического противоречия в пространстве): masked — в продакшен-логах, оригинал — в vault'е.

**Задачи:**
- T2.3.1. Развернуть HashiCorp Vault (или аналог) с auto-unseal.
- T2.3.2. Реализовать `VaultClient.store(mask, original, ttl=24h)` и `VaultClient.recover(mask, mfa_token)`.
- T2.3.3. Интегрировать TOTP MFA (pyotp) для recovery.
- T2.3.4. Логировать каждый recovery в audit trail (кто, когда, какой mask, по какой причине).
- T2.3.5. Cron-джоб для очистки истёкших TTL.

**DoD.** Инженер с MFA может восстановить PII по маске `[EMAIL:5f3a]` за < 30 секунд. Без MFA — отказ.

**KPI.** Recovery success rate: 100% для авторизованных пользователей. Время жизни PII в vault: ≤ 24 часа.

#### Эпик E2.4 — Async eval-pipeline с late annotation

**Описание.** Реализовать eval-pipeline из §3.3 `ARCHITECT.md`: rule-based проверки выполняются синхронно (в составе span'а), LLM-as-judge — асинхронно через очередь (`Redis + RQ`). Результат LLM-as-judge привязывается к уже закрытому трейсу по `trace_id` через late annotation (§7.3). Это разрешает ТП-2 (§10.4): пользователь не ждёт eval, эвал прицепляется через 5 секунд.

**ТРИЗ-обоснование.** Принцип 9 (предварительное противопоставление): precompute embedding'и golden-ответов офлайн, онлайн-eval сводится к cosine similarity. Принцип 24 (посредник): асинхронный eval-worker через очередь — пользователь получает ответ сразу, эвал прицепляется потом.

**Задачи:**
- T2.4.1. Развернуть Redis + RQ workers (отдельный процесс, не в агенте).
- T2.4.2. Реализовать `RuleBasedEvaluator` (regex, JSON-schema, blacklist).
- T2.4.3. Реализовать `LLMJudgeEvaluator` с промптами для faithfulness, answer_relevancy, completeness.
- T2.4.4. Реализовать `EmbeddingEvaluator` — cosine similarity до golden-ответа.
- T2.4.5. Late annotation: после завершения эвал-джобы, результат пишется в Hot store (ClickHouse) с `trace_id` ключом.
- T2.4.6. UI: показать eval-результат в trace-viewer в отдельной панели (если ещё не пришёл — показать «pending»).

**DoD.** Пользователь получает ответ за то же время, что и без eval. В UI через 5–30 секунд появляется eval-результат с reasoning.

**KPI.** Latency добавленная для пользователя: 0 мс. Latency eval: < 30 секунд p95.

#### Эпик E2.5 — Drift detector на embedding'ах

**Описание.** Реализовать `DriftDetector` из §4.2 `ARCHITECT.md`: каждые 15 минут сравнивает распределение embedding'ов ответов за последнее окно с baseline-окном (7 дней за вычетом последнего часа). Метрика — KL-дивергенция. При превышении p99-порога — alert. Baseline определяется по историческим данным, как в антипаттерне §8.7.

**ТРИЗ-обоснование.** Стандарт 1.1.5 (замена вещества полем): ручная проверка трейсов инженером заменяется автоматическим embedding-detection аномалий — поле (embedding-метрика) заменяет человеческий труд. Принцип 15 (динамичность): baseline-окно скользит, не фиксируется раз и навсегда.

**Задачи:**
- T2.5.1. Хранить embedding'и ответов в Hot store (ClickHouse column `response_embedding Array(Float32)`).
- T2.5.2. Cron-джоб: каждые 15 минут вычислять KL-дивергенцию последнего часа vs baseline (7д минус последний час).
- T2.5.3. Подобрать порог: p99 KL за последние 30 дней = alert threshold.
- T2.5.4. Alert в Alertmanager с лейблами `agent_id`, `kl_divergence`, `baseline_window`.
- T2.5.5. Интеграция с Phoenix UMAP-визуализатором для root-cause.

**DoD.** При дрейфе ответов (как в кейсе §9.3) alert приходит < 15 минут после начала дрейфа.

**KPI.** Drift detection latency: < 15 минут. False positive rate: < 5% (по историческим данным).

#### Эпик E2.6 — Hot/Warm/Cold tiering storage

**Описание.** Внедрить tiered storage из §4.1 `ARCHITECT.md`: Hot (ClickHouse, 14 дней, full span), Warm (Postgres, 90 дней, structure + metrics), Cold (S3 + Parquet, 1 год, агрегаты). Migration-джоб переносит данные между тирами по расписанию.

**ТРИЗ-обоснование.** Принцип 18 (использование механических колебаний): tiered retention с колеблющейся детализацией — 14 дней full, 90 дней structure+metrics, 1 год агрегаты. Принцип 17 (переход в другое измерение): трейс хранится не как один объект, а как многомерная структура (structure + content + metrics), с разной степенью детализации.

**Задачи:**
- T2.6.1. Развернуть ClickHouse с шардированием по `agent_id` и `tenant_id`.
- T2.6.2. Развернуть Postgres для Warm (join с user/tenant сущностями).
- T2.6.3. Развернуть S3 + Parquet для Cold (Athena для запросов).
- T2.6.4. Migration-джоб: ежедневно переносит трейсы старше 14 дней из Hot в Warm (со сжатием — удаляем `llm.input_text`, оставляем `llm.input_chars` и хэш).
- T2.6.5. Migration-джоб: еженедельно переносит трейсы старше 90 дней из Warm в Cold (только агрегаты).

**DoD.** Запрос за последние 14 дней — < 1 секунды. Запрос за 90 дней — < 5 секунд. Запрос за 1 год — < 1 минуты (через Athena).

**KPI.** Hot query latency: < 1 с p95. Storage cost: < $0.5/GB/месяц (Hot + Warm + Cold с учётом сжатия).

#### Эпик E2.7 — Adaptive sampling по load/error-rate

**Описание.** Расширить tail-sampler из MVP: вместо фиксированных 10% для normal-трейсов — динамическая rate в зависимости от состояния системы. Базовая адаптация (полностью динамическая — на уровне 3): при высоком load (CPU > 80%) rate снижается до 5%, при росте error-rate rate повышается до 30%. Это закладывает фундамент для Стандарта 2.2.4 (динамизированный веполь).

**ТРИЗ-обоснование.** Принцип 15 (динамичность): характеристики сэмплера должны меняться так, чтобы быть оптимальными в каждом режиме. Стандарт 2.2.4 (динамизированный веполь): поле observability адаптируется к обстановке.

**Задачи:**
- T2.7.1. Экспортировать метрики `system_cpu_ratio`, `agent_error_rate_5m` в sampler.
- T2.7.2. Реализовать policy: `if cpu > 0.8: rate = 0.05; elif error_rate > 0.05: rate = 0.3; else: rate = 0.1`.
- T2.7.3. Логировать изменения rate в audit trail.
- T2.7.4. Метрика `tail_sampler_current_rate` для мониторинга.

**DoD.** При CPU > 80% rate автоматически падает до 5%, алерт не срабатывает. При росте error_rate > 5% rate растёт до 30%.

**KPI.** Overhead reduction при пиках: 50% (по сравнению с фиксированной 10% rate).

**ТРИЗ-обоснование.** Стандарт 3.1.1 (переход к макроуровню): переход от системы (один агент) к надсистеме (организация агентов). Federation layer объединяет разрозненные observability-данные в единую карту.

**Задачи:**
- T4.4.1. Ввести `federation_trace_id` — связывает трейсы разных агентов одного пользователя за сессию.
- T4.4.2. Реализовать `FederationLayer` в API: `GET /federation/user/{user_id}/traces` возвращает связанные трейсы.
- T4.4.3. UI: «User Journey» view — карта всех трейсов пользователя за период.
- T4.4.4. Cross-agent correlation: если agent A вызвал agent B через A2A-протокол, их трейсы связываются.

**DoD.** В UI видна карта всех взаимодействий пользователя со всеми агентами за период.

**KPI.** Cross-agent trace correlation coverage: 100% для A2A-вызовов.

#### Эпик E4.5 — LLM-intrinsic trace (PoC)

**Описание.** PoC-уровневая реализация ИКР: «агент сам себя трассирует, генерируя трейс как естественный побочный продукт рассуждения». Это делается через специальный system prompt, заставляющий LLM выводить structured trace вместе с ответом. PoC проводится на одной модели (gpt-4o), не на всех. Цель — доказать жизнеспособность подхода, не внедрять в продакшен.

**ТРИЗ-обоснование.** ИКР (§10.6): «идеальная observability-система не имеет отдельных компонентов». LLM-intrinsic trace — это устранение SDK как отдельного компонента: трейс генерируется самой моделью. Стандарт 1.1.1 (синтез веполя): добавляем «поле» (structured trace) к объекту (LLM-ответу), делая невидимое (рассуждение) видимым.

**Задачи:**
- T4.5.1. Разработать system prompt, заставляющий LLM выводить JSON-трейс вместе с ответом.
- T4.5.2. Реализовать парсер intrinsic trace → standard span format.
- T4.5.3. Сравнить overhead: intrinsic trace vs SDK instrumentation.
- T4.5.4. Сравнить качество: faithfulness у intrinsic vs SDK.
- T4.5.5. Решение: продакшен-внедрение или нет (по результатам PoC).

**DoD.** PoC завершён, документ с результатами и рекомендацией.

**KPI.** Intrinsic trace overhead: 0% (по сравнению с SDK). Качество трейса: ≥ 80% от SDK-trace.

#### Эпик E4.6 — Implicit eval (качество через факт следующего действия пользователя)

**Описание.** ИКР-направленное улучшение: вместо явной LLM-as-judge оценки — implicit eval через факт следующего действия пользователя. Если пользователь после ответа агента задаёт уточняющий вопрос с негативной окраской («нет, не то»), это сигнал низкого качества. Если принимает ответ и уходит — высокий. Это бесплатная оценка, не требующая LLM-call.

**ТРИЗ-обоснование.** ИКР (§10.6): «качество оценивается самим фактом успешности следующего действия пользователя (implicit eval)». Устраняет отдельный eval-слой как таковой.

**Задачи:**
- T4.6.1. Реализовать `ImplicitEvalDetector`: классифицирует следующее сообщение пользователя (positive/neutral/negative).
- T4.6.2. Атрибут span'а `eval.implicit_score` — -1 (negative), 0 (neutral), +1 (positive).
- T4.6.3. Корреляция с explicit eval (LLM-as-judge): метрика согласованности.
- T4.6.4. Если implicit score стабильно расходится с explicit — alert (drift в eval-judge).

**DoD.** Каждый трейс имеет `eval.implicit_score` без дополнительной LLM-cost.

**KPI.** Implicit eval coverage: 100% трейсов с продолжением диалога. Согласованность с explicit eval: ≥ 70%.

---

#### Эпик E4.7 — Compact-embedding reconstruction

**Описание.** ИКР-направленное улучшение: хранение не полного трейса, а compact-embedding'а, по которому восстанавливается структура дерева. Это позволяет радикально сократить storage (в пределе — избавиться от Hot/Warm/Cold tiering). PoC-уровневая задача.

**ТРИЗ-обоснование.** ИКР (§10.6): «storage не нужен, т.к. трейсы „сжимаются" в compact-embedding'и, по которым восстанавливается дерево». Устраняет storage как отдельный слой.

**Задачи:**
- T4.7.1. Обучить модель encoding: trace tree → fixed-size embedding (например, 1024 dims).
- T4.7.2. Обучить модель decoding: embedding → approximate trace tree.
- T4.7.3. PoC: хранить только embedding + ключевые атрибуты, восстанавливать дерево по требованию.
- T4.7.4. Сравнить storage: full trace vs compact embedding.

**DoD.** PoC завершён, отчёт с результатами.

**KPI.** Storage reduction: 100× (если PoC удачен). Reconstruction accuracy: ≥ 80%.

### 7.7. Rollback-стратегия

- **Sidecar rollback:** переключить thin client на direct SDK mode (без sidecar), но с тем же API.
- **Protobuf rollback:** версионирование схемы, old consumers поддерживаются 2 версии назад.
- **Cost-aware routing rollback:** флаг `cost_aware.enabled = False` → всегда используется default-модель.
- **Federation rollback:** флаг `federation.enabled = False` → трейсы не связываются, изоляция сохранена.
- **LLM-intrinsic trace rollback:** это PoC, не в продакшене — rollback не требуется.
- **Implicit eval rollback:** флаг `implicit_eval.enabled = False` → используется только explicit eval.
- **Compact-embedding rollback:** это PoC, не в продакшене — rollback не требуется.
- **Полный уровень 4 rollback:** каждый эпик независимо отключаем, уровень 3 продолжает работать.

## 9. Рекомендации по инкрементальной реализации

### 9.1. Стратегия ветвления

Roadmap можно реализовывать тремя способами — выбор зависит от размера команды и срочности.

**Стратегия A: Последовательная (рекомендуется для команд 3–5 человек).** Каждый уровень — отдельный milestone, переход к следующему только после выполнения всех критериев выхода. Преимущество: низкий риск, предсказуемые сроки. Недостаток: 12 месяцев до финального состояния.

**Стратегия B: Параллельные стримы (для команд 8+ человек).** Уровень 1 и начало уровня 2 (E2.1 Guardrail, E2.4 Async eval) идут параллельно — guardrail и eval-очередь не зависят от MVP-компонентов, кроме трейсов. После уровня 2 можно параллельно запускать стримы «storage optimization» (E3.1, E3.4, E3.5, E3.6) и «SLO/RBAC» (E3.7, E3.8). Преимущество: сокращение времени на 30–40%. Недостаток: выше координационные накладные.

**Стратегия C: Quick-wins first (для стартапов).** Сначала делаются эпики с быстрой отдачей: E1.4 Cost-трекинг, E1.6 Ring buffer, E2.1 Guardrail, E2.4 Async eval. Остальное — по мере появления ресурсов. Преимущество: быстрый ROI. Недостаток: некоторые архитектурные улучшения (E3.4 Tree-compression) откладываются, может потребоваться рефакторинг.

### 9.2. Параллелизация внутри уровня

**На уровне CRITICAL (2–3 месяца)** можно параллелить:
- Стрим A: E2.1 Guardrail + E2.2 Field-aware PII + E2.3 Vault + E2.8 Compliance-catalog (security-стек, одна подкоманда).
- Стрим B: E2.4 Async eval + E2.5 Drift detector (eval-стек, другая подкоманда).
- Стрим C: E2.6 Tiered storage + E2.7 Adaptive sampling (инфра-стек).
- Завершение: интеграция всех трёх стримов в общую систему.

**На уровне production-ready (6 месяцев)** можно параллелить:
- Стрим A: E3.1 Adaptive sampling + E3.2 Span-aggregation + E3.3 Adaptive eval-sampling (производительность).
- Стрим B: E3.4 Tree-compression + E3.5 Tiered retention + E3.6 Embedded subtree (storage).
- Стрим C: E3.7 SLO/SLA + E3.8 Multi-tenant RBAC (эксплуатация).

**На уровне Улучшения (12 месяцев)** параллелизация ограничена зависимостями:
- Сначала: E4.2 Protobuf-first (база для всего).
- Параллельно: E4.1 Sidecar-SDK (после E4.2) + E4.3 Cost-aware routing + E4.4 Federation.
- PoC-задачи (E4.5, E4.6, E4.7) — отдельная research-команда, не блокирует основной стрим.

## 10. Заключение

Настоящий `ROADMAP.md` разворачивает §12 «Roadmap внедрения» из `ARCHITECT.md` в четырёхуровневый план: MVP (4–6 недель) → CRITICAL (2–3 месяца) → production-ready (6 месяцев) → Улучшения production-ready (12 месяцев). Каждый уровень является самостоятельной поставкой ценности и не нарушает работу предыдущего — это фундаментальный принцип non-contradiction, соблюдённый на всех уровнях декомпозиции.

Применение ТРИЗ-методологии к roadmap выражается в двух аспектах. Во-первых, все 15 улучшений из §11.1 `ARCHITECT.md` явно распределены по уровням (см. §3), что обеспечивает отсутствие пропусков и противоречий с исходной архитектурой. Во-вторых, каждый эпик имеет явное ТРИЗ-обоснование — указание на конкретный принцип (из 40 приёмов Альтшуллера) или стандарт (из 76 стандартов), что позволяет команде понять не только «что» делается, но и «почему» именно так. Это критически важно для архитектурных решений, которые иначе превратились бы в произвольные предпочтения.

Сквозная KPI-карта (см. §8) показывает измеримый прогресс: идеальность растёт от 0.83 на MVP до 3.6 на финальном уровне, что соответствует росту в 4.3 раза (по §11.4 `ARCHITECT.md`). Параллельно overhead снижается с 5% CPU до 0.6 мс p99, storage cost для длинных трейсов — на 75–90%, поддерживаемые языки расширяются с одного Python до трёх (Python, JS, Go). Каждая метрика имеет целевое значение на каждом уровне — это позволяет стейкхолдерам отслеживать прогресс без технических деталей.

Дальнейшие шаги команды: (1) зафиксировать выбранный уровень (MVP или сразу CRITICAL, если есть ресурсы), (2) перенести эпики в трекер задач (Jira/Linear) с оценкой в story points, (3) назначить ответственных за каждый эпик, (4) начать с первого эпика уровня. `ROADMAP.md` intentionally написан на уровне эпиков и задач, а не конкретного кода — это позволяет сохранить гибкость в выборе реализаций, не нарушая архитектурных контрактов из `ARCHITECT.md`.
